# Деплой и память: как выложить бота в интернет, чтобы он не забывал разговор

> 📖 Красиво смотреть: `Cmd+Shift+V` (Windows: `Ctrl+Shift+V`).

Этот файл отвечает на два вопроса новичка:
1. Как сделать, чтобы бот **помнил** разговор?
2. Как выложить бота в интернет, чтобы он работал **24/7**, а не только у тебя на компьютере?

---

## Часть 0. Сначала — что вообще такое «память» у бота

Модель ИИ **ничего не запоминает сама**. Каждый твой вызов к ней — это чистый лист:
она не знает, о чём вы говорили минуту назад.

«Память» бота — это обман зрения. На самом деле происходит так:
**перед каждым новым вопросом ты заново отправляешь модели ВСЮ историю разговора**,
и она как будто «помнит» — а на самом деле просто прочитала всё с начала.

```
Вопрос 1:                     [Вопрос 1]                              → модель отвечает
Вопрос 2: [Вопрос 1][Ответ 1] [Вопрос 2]                              → модель отвечает
Вопрос 3: [Вопрос 1][Ответ 1] [Вопрос 2][Ответ 2] [Вопрос 3]         → модель отвечает
```

Отсюда два практических следствия:
- Чем длиннее разговор — тем больше текста отправляется каждый раз, а значит **дороже и медленнее**.
- Историю разговора нужно **где-то хранить**, чтобы было что пересылать. Вот про это и весь файл ниже.

Есть два вида такого хранения:

- **Короткая память** — хранить историю, пока открыт разговор (одна сессия). Закрыл вкладку — забыл.
- **Долгая память** — сохранить историю **на диск/в базу**, чтобы бот помнил тебя даже после
  перезапуска, и по каждому пользователю отдельно.

## Часть 0.5. «Неужели каждый раз шлётся ВСЁ?» — оптимизации

Логичный вопрос: если перед каждым сообщением заново пересылать всю историю — это
же гора токенов? Разберём — здесь есть важные нюансы.

**Сначала про размер.** У современных моделей контекстное окно **огромное — до
1 000 000 токенов** (Gemini, Claude, Qwen3 Max, DeepSeek и др.; у лёгкой локальной
llama3.2 — порядка 128k). Миллион токенов — это примерно 700+ страниц текста. То
есть проблема обычно **не в том, что «история не влезет»** — почти всегда влезает.

Проблема в другом: даже когда влезает, гонять гигантский контекст **каждый раз** —
это:
- 💸 **дорого** — платишь за каждый входной токен, и за длинную историю платишь
  СНОВА на каждом сообщении;
- 🐢 **медленно** — модель перечитывает всё заново;
- 🎯 **хуже по качеству** — на очень длинном контексте модель начинает «терять
  середину» (важное в центре истории замечает хуже).

Поэтому историю не тащат «в лоб», а оптимизируют. Главные приёмы:

| Приём | Что делает |
|---|---|
| **Prompt caching** (кэш промпта) | Провайдер запоминает неизменное **начало** запроса и не считает его заново. История как бы отправляется, но платишь **~в 10 раз меньше** и ответ быстрее. Включается почти автоматически (Anthropic / OpenAI / Google). |
| **Sliding window** (скользящее окно) | Держим только **последние N** сообщений, старое просто отбрасываем. Самый простой способ. |
| **Summarization / compaction** (сжатие в резюме) | Старую часть заменяем коротким пересказом: 20 сообщений → 2 строки «клиент Дима, хочет стрижку в пятницу». |
| **RAG по истории** (поиск по смыслу) | Всю историю храним в базе, а модели даём **только релевантные** под текущий вопрос куски (через эмбеддинги), а не всё подряд. Так работает CrewAI с `memory=True`. |

**Ключевая мысль — это ДВЕ разные вещи (в Части 0 они слиты):**
- **что хранить** — всю историю, в файле/базе, чтобы пережить перезапуск;
- **что из этого реально отправлять/обрабатывать каждый раз** — вот тут и живут
  кэш, окно, сжатие и RAG.

Наивный вариант из Части 0 («шлём всё») — это когда второй вопрос ещё не решён.
Как только диалоги растут, включают сжатие или RAG, а prompt caching делает так,
что даже большой неизменный «хвост» истории стоит копейки.

> 🧭 На старте (учебные боты, короткие диалоги) об этом можно **вообще не думать**
> — «шлём всё» отлично работает и стоит копейки. Оптимизации нужны, когда история
> становится длинной или пользователей много.

## Часть 1. Как это включить — под каждый вариант кода

### Голый код (`01-pure_python`)
Ты сам собираешь список сообщений и отправляешь его целиком (это и есть «короткая память»).
В `chat_web.py` это уже сделано — посмотри на переменную `history`.

Для **долгой** памяти (пережить перезапуск) — сохраняй историю в файл или базу.
Готовый пример на файле — `01-pure_python/10_memory.py`.

### OpenAI Agents SDK — `Sessions`
Фреймворк умеет сохранять историю сам, если дать ему «сессию» с файлом-базой:
```python
from agents import Agent, Runner, SQLiteSession

# "user_123" — id разговора/пользователя. conversations.db — файл на диске.
session = SQLiteSession("user_123", "conversations.db")
result = Runner.run_sync(agent, "Привет!", session=session)
# Следующий вызов с session=session тем же ID — бот помнит прошлый разговор,
# даже если ты перезапустил программу.
```

### CrewAI — включается одним флагом
```python
crew = Crew(agents=[...], tasks=[...], memory=True)
```
Внутри CrewAI сохраняет память локально (в виде «эмбеддингов» — не углубляйся, просто
знай, что это способ хранить смысл текста). По умолчанию для этого нужен ключ
`OPENAI_API_KEY` — CrewAI использует эмбеддинги OpenAI, даже если сама модель у тебя другая.

### LangGraph — самый гибкий вариант (`checkpointer`)
```python
from langgraph.checkpoint.memory import MemorySaver   # хранит в оперативной памяти (пропадёт при перезапуске)
# from langgraph.checkpoint.sqlite import SqliteSaver  # хранит в файле (переживёт перезапуск)

graph = builder.compile(checkpointer=MemorySaver())
config = {"configurable": {"thread_id": "user_123"}}   # id конкретного разговора
graph.invoke({...}, config)   # LangGraph сам подставит историю по этому thread_id
```

> ⚠️ **Важный момент.** Рано или поздно разговор станет таким длинным, что превысит
> лимит модели («контекстное окно» — максимум текста за раз). Тогда старую часть
> истории не хранят дословно, а **сжимают в короткое резюме** — это называется
> compaction. У фреймворков для этого есть готовые настройки.

## Куда выкладывать (важно)

Наш бот — это **Gradio**, то есть постоянно работающий сервер. Значит нужен
**обычный хостинг** (Render / Railway / Hugging Face Spaces), а НЕ serverless.

> ⚠️ **Vercel для нашего бота не подходит** — он serverless (код «просыпается» на
> один запрос и засыпает), это для сайтов на JS, а Gradio на нём не живёт.
> (Vercel + Supabase — отличная связка, но для фронтенда на Next.js, не для
> Python-Gradio.) Про все хостинги и цены — в `HOSTING.md`.

Дальше — деплой **в два шага**: сначала просто выложим бота (Шаг 1), потом
подключим базу **Supabase**, чтобы он помнил записи (Шаг 2). Ниже показываю на
**Render**; на Railway всё почти так же, а **Hugging Face Spaces** — самый простой
бесплатный вариант для Gradio.

## Шаг 1. Выложить бота (поговорить в рамках сессии)

Цель шага: бот работает по публичной ссылке и помнит разговор, **пока открыт чат**
(одна сессия). Записи клиентов пока в файле и могут теряться при перезапуске
сервера — это починим в Шаге 2.

### Что именно выкладываем (нюанс)

Файлы из `01-pure_python` (`03_judge.py`, `06_router.py` …) — это скрипты: запустились,
напечатали в терминал и завершились. Их **нельзя задеплоить** — с ними некому
разговаривать.

Выкладывают файл, который **постоянно слушает сообщения**:
- `chat_web.py` — простой чат на Gradio;
- `05-example_bot/bot.py` — наш бот-барбершоп (его и берём дальше).

### Готовим бота к серверу (3 вещи — уже сделаны в проекте)

1. **Модель — облачная.** На сервере Ollama нет, поэтому в `bot.py` стоит
   `PROVIDER = "gemini"`. Нужен ключ `GOOGLE_API_KEY`.
2. **`gradio` в `requirements.txt`.** Хостинг ставит только то, что там указано —
   без этой строки бот не соберётся.
3. **Порт от хостинга.** Бот уже читает его сам:
   ```python
   .launch(server_name="0.0.0.0", server_port=int(os.environ.get("PORT", 7860)))
   ```

### Деплой на Render — по шагам

1. **Залей проект на GitHub** (см. `RESOURCES.md` или попроси Claude помочь с `git`).
2. **render.com → New → Web Service** → подключи свой репозиторий.
3. Укажи команды:
   - **Build Command:** `pip install -r requirements.txt`
   - **Start Command:** `python 05-example_bot/bot.py`
4. **Environment** → добавь `GOOGLE_API_KEY = твой_ключ` (как в `.env` на компьютере).
5. **Create Web Service** → Render соберёт проект и выдаст **публичную ссылку**.
6. Открой ссылку — общайся с ботом в браузере. 🎉

> ⚠️ На бесплатном тарифе Render сервис **«засыпает»** после ~15 минут простоя;
> первый запрос после паузы отвечает через ~30–60 секунд — это нормально.

> **Railway:** *New Project → Deploy from GitHub → Start Command → ключи в Variables*.
> **Hugging Face Spaces:** создаёшь Space, загружаешь файлы, он сам поднимает чат —
> самый простой бесплатный путь для Gradio. См. `HOSTING.md`.

Готово: бот живой и отвечает. Но записи клиентов пока в файле на сервере, а он
стирается при перезапуске/редеплое. Чтобы записи не терялись → Шаг 2.

## Шаг 2. Подключить Supabase (чтобы бот помнил записи НАВСЕГДА)

**Supabase — это облачная база Postgres** с удобной админкой. Она живёт **отдельно**
от бота: бота можно передеплоить, перезапустить, сменить хостинг — а записи
останутся в базе.

Наш `bot.py` **уже готов** к этому. Функция `record_lead` сама смотрит на переменную
`DATABASE_URL`:
- есть `DATABASE_URL` → пишет в базу (Supabase);
- нет → пишет в файл `leads.json` (как локально).

**Код менять не нужно** — только дать боту адрес базы.

### По шагам

1. Заведи проект на **supabase.com** (бесплатно).
2. **Settings → Database → Connection string → URI.** Скопируй строку вида:
   ```
   postgresql://postgres:[ПАРОЛЬ]@db.xxxx.supabase.co:5432/postgres
   ```
   (`[ПАРОЛЬ]` — тот, что задал при создании проекта.)
3. Дай эту строку боту как `DATABASE_URL`:
   - **на Render** — Environment → добавь `DATABASE_URL = postgresql://...`;
   - **локально** (по желанию) — впиши `DATABASE_URL=postgresql://...` в `.env`.
     Тогда даже с ноутбука бот пишет записи в облачную базу.
4. Перезапусти бота. При первой записи он **сам создаст таблицу** `leads`
   (`CREATE TABLE IF NOT EXISTS`) — настраивать вручную ничего не нужно.

### Посмотреть записи глазами

Supabase → **Table Editor** → таблица **`leads`**. Клиент записался в чате → строка
появилась в таблице. Наглядная демонстрация «настоящей памяти» бота.

### Схема (кто где живёт)

```
🤖 Бот (Gradio)   →  Render / Railway / HF Spaces
        │  DATABASE_URL
        ▼
🗄️ База (записи)  →  Supabase (Postgres, отдельно)
```

### Грабли (частые)

- **SSL.** Supabase требует защищённое подключение. Обычно строка из URI работает
  как есть; если `psycopg2` ругается — добавь в конец `?sslmode=require`.
- **Direct vs пул.** У Supabase две строки: **Direct** (порт `5432`) и
  **Connection Pooler** (порт `6543`). Нашему боту подойдёт любая; ждёшь много
  одновременных пользователей — бери пул (`6543`).
- **Засыпание.** На бесплатном тарифе проект Supabase засыпает после ~7 дней
  простоя — можно разбудить из панели.

> 💡 Чем Supabase удобнее «встроенной» базы хостинга: она отдельная — не удаляется
> вместе с сервисом и легко переносится между хостингами.

## Что добавить под другой фреймворк

Разница при деплое минимальна — поставить нужный пакет и подключить память.

### Голый код / Gradio
- Ничего особенного: `requirements.txt` (там уже есть `gradio`). Самый простой вариант.

### OpenAI Agents SDK
- В `requirements.txt`: `openai-agents`; ключ `OPENAI_API_KEY`.
- Память: `SQLiteSession(...)` (см. Часть 1). «Слушающую» часть (Gradio/сайт) пишешь сам.

### CrewAI
- В `requirements.txt`: `crewai`. Ключ модели (`GOOGLE_API_KEY`) + отдельно
  `OPENAI_API_KEY`, если включена память (`memory=True` — эмбеддинги через OpenAI).
- Память: `Crew(..., memory=True)`.

### LangGraph
- В `requirements.txt`: `langgraph`. Память: `checkpointer=SqliteSaver(...)` + `thread_id` (см. Часть 1).
- Есть «родная» **LangGraph Platform** (деплой + память + мониторинг из коробки).

## Короткий маршрут «хочу протестировать прямо сейчас»

1. Залей проект на GitHub.
2. На Render задеплой `05-example_bot/bot.py` (Start Command: `python 05-example_bot/bot.py`).
3. Впиши `GOOGLE_API_KEY` в Environment → открой ссылку Render → общайся с ботом. **(Шаг 1)**
4. Когда захочешь, чтобы записи не терялись — заведи Supabase и добавь
   `DATABASE_URL` в Environment. **(Шаг 2)**
